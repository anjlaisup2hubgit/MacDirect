## Project in one paragraph
iMCQ is a mobile-first Macquarie University campus map (Node/Express serving static HTML/JS, Leaflet map, popups over `index.html`). Goal of the current work: users log in, guests browse through a guest view, and users follow societies. Leaders post society events (with an optional photo) in the Add event plan popup. Backend is Supabase (Postgres + Auth + row-level security). The browser talks to Supabase directly; Express serves pages, the map, and `GET /api/config` (public URL and publishable key from `.env`).

## Decisions already made (do not re-ask)
* Backend: Supabase, not MySQL/Docker. The README says so.
* Name: MacDirect everywhere users can see it (renamed from iMCQ on 2 Nov 2026; package name `macdirect`). Left as `imcq-...` on purpose: localStorage/sessionStorage keys (renaming would reset saved language and guest choice), the calendar `UID ...@imcq` suffix, `.claude/launch.json` (`mcq-imap`), `.claude/agents/*`, `tools/trace-lit-paths/*` comments and the older step text in this file.
* Leaders: choose a society at sign-up, an admin approves in the "Leader requests" section of User Settings (step 23). The Supabase dashboard still works too.
* Guests: can browse the map, societies and food; follow, event plan and the Calendar show "Log in to ..." (the Calendar is login-only). Leaders post society events (with an optional photo) in the Add event plan popup.
* Roles: `profiles.role` is `student` or `admin`. A leader is a user with an approved `society_leaders` row.

## Where things are
* Pages are popups over the map: `public/index.html` plus `public/js/pages/*.js` (societies, events, event-plan, food, settings). Popups are built with `createPopup` in `public/js/components/popup.js`.
* Auth: `public/js/lib/auth.js` (global `auth`: `ready`, `user`, `profile`, `leaderships`, `onChange`, `signIn`, `signUp`, `signOut`, `continueAsGuest`, `requireLogin`, `listSocieties`, `myFollows`, `setFollow`, `approvedSocieties`, `listEvents`, `saveEvent`, `deleteEvent`, `updateDisplayName`, `listMyPlans`, `savePlan`, `deletePlan`, `clearPlans`, `listSocietyImages`, `uploadSocietyImage`, `deleteSocietyImage`, `updateSocietyHashtags`). Language: `public/js/lib/i18n.js` (`t(key)`, `i18nLang()`, `setLang()`; keys are English text, dictionary has `zh`, `ar`, `yue`, `vi`, `hi`, `el`, `fil`, `it`, `ko`, `pa` and `ne`; `I18N_LOCALES` maps each to a date locale). Login UI: `public/login.html`, `public/js/pages/login.js`.
* Database: `database/schema.sql` (tables, RLS, grants, sign-up trigger), `database/seed.sql`. Not applied automatically; run in the Supabase SQL editor.
* Server: `server.js` loads `.env` and serves `/api/map`, `/api/config` and the JSON-backed `/api/food`.
* Secrets: `.env` (gitignored). `.env.example` lists the variable names.

## Running and testing
* `npm install` then `npm start`. Default port 3000; if busy the dev preview used 3001.
* Visitors with no session and no guest choice are redirected to `/login.html`. To test as a guest, use "Continue as guest". `localhost` and `127.0.0.1` have separate browser storage, which is a quick way to get a logged-out session without signing anyone out.
* Do not create accounts on the live Supabase project from automated tests; ask the project owner to sign up manually.

## Known gaps and gotchas
* Photos on private plans go in the PUBLIC `society-images` bucket under `<user id>/plans/`; only the random file name keeps them unguessable. Not tested: that deleting a plan really removes the file (needs the select policy added in the "Photos on private event plans" block).
* Cover images: the bucket is public, so anyone with an image URL can view it; there is no moderation (shows immediately). Deleting a society removes its `society_images` row but NOT the file in Storage (orphaned file; delete it in the dashboard). The SQL must be run by hand in Supabase; until then guests just see no images (the app does not break). Never tested with a real approved leader account. The section's messages use a local `flash()` in `event-plan.js` (the settings one is private). Uploading fires `society-images-changed`, which the Societies popup listens for.
* The Calendar popup keeps URL `/?events`, id `events-popup` and file `events.js`. Guests open it normally and see its in-popup gate (no login dialog). Nav label "Societies" is a separate i18n key from the popup title "On-campus Societies".
* Plans saved before step 11 stay in the browser's `localStorage` key `plannedEvents` and are no longer shown.
* The login page's language select also reloads; typed email and display name survive via sessionStorage, but the password, the active tab and any message do not.
* Language changes reload the page (`/?tasks`, reopening User Settings). Static HTML uses `data-i18n` attributes; JS-built UI calls `t('English text')`. Database content (societies, events, food, building names/descriptions/addresses) and card dates stay English/en-AU; the calendar month title follows the language. `auth.requireLogin(message)` takes the full English key (e.g. 'Log in to follow societies'), which must exist in the dictionary. Add new UI text to every dictionary or it shows in English. Arabic sets `dir="rtl"` on `<html>`.
* Leaders post society events in the Add event plan popup ("Add for" select) or by pressing Post on a private plan in the Calendar; the Calendar also offers Edit/Delete on their society cards. Deleting an event removes its poster file; replacing a poster removes the old file. Leaders can update only `societies.hashtags` (column grant), not other society fields.
* The Task Plan view is dropped, and its route, data and the MySQL-era leftovers (Docker files, `db.js`, the old AI route, `import-geojson.js`) are deleted.
* The empty `events.html`, `event-plan.html`, `food.html` were deleted; the icon SVG now lives in `docs/`.
* Sample events seed as the first admin (`created_by` must be a real user), so run `seed.sql` events only after an admin exists. Do not re-run the societies insert (names are unique).
* Event times in Supabase are `time` values (`12:00:00`); the UI expects strings like `12:00pm`, so format when Step 6 lands.
* If email confirmation is on in Supabase, sign-up needs a confirm-then-login round trip; the leader request is filed on first login from sign-up metadata.
